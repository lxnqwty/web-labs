# Отчёт по лабораторной работе №6

**Тема:** Vue 3 — клиент API, mock и состояния пользовательского интерфейса.

## Цель работы

Отделить интерфейс от источника данных: реализовать API-модуль с функциями получения и создания активностей, mock-реализацию и HTTP-ветку на основе `fetch`. Обеспечить отображение состояний загрузки, пустого списка, данных и ошибки, а также обработку отказов и защиту от повторной отправки формы.

## Выполненная работа

1. Создан файл `frontend/.env.example` с адресом будущего API `VITE_API_BASE_URL=http://localhost:5000`. Локальный файл `frontend/.env` исключён из Git через `.gitignore`.
2. Создан каталог `frontend/src/api/` с двумя модулями: `mockTickets.js` и `tickets.js`.
3. В `mockTickets.js` реализованы асинхронные операции получения и создания записей с задержкой около 500 мс. Mock возвращает ответы с кодами 200, 201, 400 и 500; серверные `id` и `number` формируются в mock.
4. В `tickets.js` реализованы функции `getTickets()` и `createTicket(body)`. Страницы обращаются только к этим функциям и не импортируют mock. Переключатель `USE_MOCK` позволяет перейти на HTTP-запросы через встроенный `fetch` без переписывания страниц.
5. Для HTTP-ответов проверяется `response.ok`. Ответы 400 и 500 преобразуются в ошибку с HTTP-статусом. Сетевой сбой обрабатывается отдельно и не подменяется статусом 500.
6. В `TicketList.vue` добавлена асинхронная загрузка при открытии маршрута. Состояние экрана хранится в одном поле `screen`: `loading`, `empty`, `data` или `error`. Состояния взаимоисключающие; при ошибке доступна повторная загрузка.
7. В `TicketNew.vue` создание выполняется через `createTicket()`. Новая запись добавляется в общее хранилище из объекта ответа API; клиентская форма не генерирует `id` и `number`.
8. Добавлена блокировка повторной отправки через `isSubmitting`, ранний выход при повторном вызове и снятие блокировки в блоке `finally`. Во время запроса кнопка отключена и показывает текст «Создаём…».
9. Для демонстрации отказов HTTP 400 и HTTP 500 добавлены учебные переключатели в форме. Они позволяют пройти серверную ветку ошибки, не обходя обычную клиентскую валидацию. Ошибки 400, 500 и отсутствие сетевого ответа отображаются разными сообщениями.
10. README дополнен ссылкой на настоящий отчёт ЛР6; остальные разделы документации сохранены.

## Контракт API

| Функция | Назначение | Результат |
|---|---|---|
| `getTickets()` | Получить список активностей | Promise с массивом записей |
| `createTicket(body)` | Создать активность | Promise с созданной записью |

Для будущего backend используются маршруты `GET /api/tickets` и `POST /api/tickets` на базовом адресе `http://localhost:5000`.

## Проверочные сценарии

| Сценарий | Как воспроизвести | Ожидаемый результат |
|---|---|---|
| Загрузка | Открыть маршрут `/` | На время задержки показывается «Загрузка активностей…» |
| Данные | Открыть список с обычным mock | После загрузки отображается таблица из трёх записей |
| Пустой список | Временно установить `mockSettings.emptyList = true` в `mockTickets.js` и перезагрузить список | Появляется состояние «Записей пока нет» |
| Ошибка списка | Установить `mockSettings.forceListError = true` в `mockTickets.js` | Появляется состояние ошибки и кнопка повторной загрузки |
| Успешное создание | Заполнить валидную форму и отправить | Возвращённая mock запись с серверными `id` и `number` появляется в списке |
| HTTP 400 | В форме включить «Имитировать ответ сервера HTTP 400» и отправить валидные данные | Сообщение «Проверьте поля: сервер отклонил введённые данные» |
| HTTP 500 | В форме включить «Имитировать ответ сервера HTTP 500» и отправить валидные данные | Сообщение «Сервер не смог обработать запрос…»; запись не добавляется |
| Нет связи | Установить `USE_MOCK = false`, оставить API на порту 5000 незапущенным и отправить форму | Срабатывает сетевой сценарий; сообщение «Нет связи с сервером…» |
| Защита от двойной отправки | Во время задержки mock быстро нажать кнопку создания несколько раз | Кнопка disabled; создаётся одна запись |
| Снятие блокировки | Воспроизвести HTTP 500, затем исправить сценарий и отправить снова | После отказа кнопка снова активна, введённые поля сохранены |

## Проверка Network и ограничения

При `USE_MOCK = true` mock вызывается напрямую внутри приложения, поэтому отдельный HTTP-запрос в Network не появляется. Это ожидаемое поведение выбранной mock-реализации; для такого режима методичка допускает пояснение «mock без HTTP» с демонстрацией кода и консоли.

Для проверки настоящего сетевого отказа необходимо установить `USE_MOCK = false`. Тогда браузер выполняет запрос к `http://localhost:5000/api/tickets`; при незапущенном backend запрос завершается сетевой ошибкой. Реальный backend в рамках ЛР6 не создаётся.

Скриншоты из браузера в этот отчёт не включены: их необходимо сделать в локально запущенном приложении, если преподаватель требует визуальные подтверждения Network. Нельзя считать прямой вызов mock реальным HTTP-запросом.

## Вывод

В ходе выполнения лабораторной работы интерфейс цифрового профиля был отделён от реализации источника данных с помощью API-модуля. Реализованы mock и подготовленная HTTP-ветка на `fetch`, четыре состояния списка, обработка HTTP 400 и 500 и отдельная обработка отсутствия связи. Создание активности выполняется асинхронно, получает идентификатор и номер из ответа, а блокировка кнопки предотвращает повторную отправку. Проект подготовлен к подключению реального API на адресе `http://localhost:5000`.
