# Отчёт по лабораторной работе №8

**Тема:** REST API: создание, чтение, назначение исполнителя и изменение статуса заявки.

## Цель работы

Реализовать REST-маршруты для основного ресурса учебного проекта, добавить серверную валидацию, хранение заявок в памяти, отдельные операции назначения исполнителя и изменения статуса, а также безопасную обработку неожиданных ошибок.

## Выполненная работа

1. В backend добавлена модель `Ticket` и DTO для создания, назначения исполнителя, смены статуса и ответа API.
2. Реализован singleton-сервис `TicketService`, который хранит заявки в памяти, выдаёт последовательные `id` и номера и централизует правила переходов.
3. Добавлен `TicketsController` с маршрутами:
   - `POST /api/tickets`;
   - `GET /api/tickets`;
   - `GET /api/tickets/{id}`;
   - `PATCH /api/tickets/{id}/assignee`;
   - `PATCH /api/tickets/{id}/status`.
4. При создании сервер самостоятельно устанавливает статус `New`, генерирует идентификаторы и оставляет `assigneeUserId` пустым.
5. Добавлена проверка длины темы (5–80), описания (10–500) и положительного `categoryId`. Ошибки входного DTO автоматически возвращаются как `400 Bad Request`.
6. Пустой список возвращается с `200 OK` и телом `[]`; неизвестный идентификатор — с `404 Not Found`.
7. Назначение исполнителя и смена статуса реализованы отдельными PATCH-маршрутами. Для перехода в `InProgress` нужен назначенный исполнитель и совпадающий заголовок `X-User-Id`; недопустимый переход возвращает `409 Conflict`.
8. Неожиданные исключения журналируются через `ILogger`. Клиент получает безопасный `ProblemDetails`, а не stack trace.
9. Настроен CORS для локального Vue dev-сервера на порту 5173.
10. Клиентский API-модуль по умолчанию переключён с mock на настоящий backend; добавлены функции чтения одной заявки, назначения и смены статуса. Mock можно включить переменной `VITE_USE_MOCK=true`.
11. Добавлена Postman-коллекция в `docs/api-collection/tickets.postman_collection.json` с основными запросами и проверками кодов 201, 400, 404 и 409.
12. Обновлены README и контракт API.

## Запуск и проверка

Из корня репозитория:

```bash
cd backend
dotnet restore
dotnet run
```

Swagger доступен по адресу `http://localhost:5000/swagger`. Коллекцию Postman можно импортировать из `docs/api-collection/tickets.postman_collection.json`; базовый URL задан переменной `baseUrl`.

Проверки коллекции:
- успешное создание — `201`, ответ содержит `id`, `number` и `status: New`;
- короткая тема — `400`;
- неизвестный id — `404`;
- смена статуса без назначенного исполнителя — `409`;
- назначение исполнителя и корректный переход — `200`.

## Логирование

При неожиданном исключении контроллер пишет структурированную запись с операцией, идентификатором заявки (если доступен) и типом исключения. Пример формата записи:

```text
fail: backend.Controllers.TicketsController[0]
      ChangeTicketStatus failed; ticketId=1; error=InvalidOperationException
```

Это пример формата, а не снимок фактического запуска. Перед сдачей следует запустить backend локально и приложить реальный фрагмент консоли после тестового исключения, затем удалить тестовый сбой.

## Ограничения

Хранилище singleton находится в оперативной памяти процесса: данные исчезают после перезапуска backend. PostgreSQL и полноценная аутентификация не входят в ЛР8. Заголовок `X-User-Id` используется как учебный способ передать идентификатор исполнителя; он не заменяет реальную систему входа.

Сборка и HTTP-проверки не запускались в среде редактирования GitHub. Их необходимо выполнить локально командами выше.

Добавлены DTO-валидация, ответы 400/404/409, хранение в памяти, безопасная обработка неожиданных ошибок и Postman-коллекция. Клиентский API-модуль подготовлен к работе с backend.
